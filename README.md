# Школа Буркова: сбор и анализ тематических данных

Проект анализирует тематическую структуру научной школы вокруг
исследователя Буркова: как темы публикаций распределены между
участниками школы и как это распределение меняется по годам.

Весь код — в `main.ipynb`. Этот README описывает, откуда берутся
данные и как устроен API, чтобы не приходилось каждый раз заново
разбираться в переписке с куратором.

## Почему через API, а не напрямую в БД

Прямого доступа к базе данных на практике не даёт никто — доступ к
тестовым серверам ограничен сетью института. Поэтому весь сбор данных
идёт через REST API:

```
http://193.232.208.28/api/v2.5
```

Без ключей/токенов, обычные GET-запросы с параметрами в URL.

## Общая схема пайплайна

```
file.csv (id + ФИО участников школы)
        │
        ▼
┌───────────────────────────────────────────┐
│ 1. get_factors  → справочник тем           │  →  factors.json
│    (уровни 0, 1, 2)                        │
├───────────────────────────────────────────┤
│ 2. get_profile для каждого автора          │  →  author_year_vectors_sid=….json
│    по каждому году отдельно                │
├───────────────────────────────────────────┤
│ 3. get_profile для каждого автора          │  →  author_overall_vectors_sid=….json
│    сразу за весь период (begin..end)       │
├───────────────────────────────────────────┤
│ 4. authors/search по id                    │  →  author_fio.json
│    (получить ФИО по идентификатору)        │
└───────────────────────────────────────────┘
        │
        ▼
   аналитика и визуализация (раздел 3 ноутбука)
```

Раздел 1–2 ноутбука выполняет весь сбор и один раз сохраняет
результат на диск в JSON — дальше (раздел 2.5 и весь раздел 3)
работа идёт уже с локальными файлами, без повторных запросов к API.

## Параметр `sid`: как он устроен

`sid` — это три цифры, каждая означает своё:

| Позиция | Что кодирует | Значения |
|---|---|---|
| 1-я цифра | тип текста, по которому строился профиль | `1` — по аннотациям, `2` — по полным текстам |
| 2-я цифра | уровень детализации темы (= `clf_level` в `get_factors`) | `0` — метапрофиль, `1` — базовый, `2` — детальный |
| 3-я цифра | зарезервирована, пока всегда `0` | `0` |

Отсюда и реально используемые значения: `100, 110, 120, 200, 210, 220`.

**Важно:** 2-я цифра `sid` — это и есть `clf_level`, который нужно
передать в `get_factors`, чтобы расшифровать номера тем (`c_f_id`) из
ответа `get_profile` в человекочитаемые названия. Например, `sid=110`
→ темы нужно смотреть в `get_factors?clf_level=1`; `sid=120` → в
`get_factors?clf_level=2`. Это не два независимых параметра, а один
параметр, определяющий другой — если менять `sid`, обязательно менять
и то, какой уровень факторов подгружать.

## Справочник эндпоинтов

| # | Назначение | Пример запроса |
|---|---|---|
| 1 | Профиль автора, базовый уровень тем (`clf_level=1`) | `.../authors/analysis/get_profile?id=53&sid=110&begin_year=2024&end_year=2024` |
| 2 | Профиль автора, детальный уровень тем (`clf_level=2`) | `.../authors/analysis/get_profile?id=7&sid=120&begin_year=2000&end_year=2025` |
| 3 | Справочник тем — все три уровня | `.../classifications/get_factors?clf_level=0` (аналогично `=1`, `=2`) |
| 4 | Поиск автора по ФИО | `.../authors/search?fio=Бурков` |
| 5 | Поиск автора по id (обратный поиск, для получения ФИО) | `.../authors/search?id=7` |
| 6 | Счётчик результатов поиска по ФИО | `.../authors/search?fio=а&count=true` → `[{"count":77525}]` |
| 7 | Поиск публикации по id | `.../publications/search?id=7` |
| 8 | Поиск публикаций по названию (текстовый поиск) | `.../publications/search?title=управление` |

Параметры `begin_year`/`end_year` в `get_profile` задают промежуток
лет: если равны — профиль за один конкретный год, если разные —
агрегированный профиль за весь промежуток.

### Пример ответа `get_profile`

```json
{
  "clf_level": 1,
  "entity_type": "person",
  "isand_id": 53,
  "profile_type": 1,
  "factors": {
    "7": 0,
    "43": 0.13933218,
    "2040": 0.6491327,
    "2045": 0.14732143
  }
}
```

`factors` — это и есть тематический вектор: ключ — `c_f_id` темы (см.
`get_factors`), значение — нормированный вес темы в профиле (сумма
весов ≈ 1). `isand_id` дублирует `id` из запроса, `profile_type`
дублирует вторую цифру `sid`.

### Пример ответа `get_factors`

```json
[
  {"c_f_id": 7,  "c_f_name": "Алгебра и теория чисел"},
  {"c_f_id": 15, "c_f_name": "Геометрия и топология"}
]
```

Простой список пар «id темы → название». В `main.ipynb` он
преобразуется в словарь `{c_f_id: c_f_name}` отдельно для каждого
уровня — это и есть `factors.json`.

## Найденные нюансы API (не задокументированы официально)

- **Параметр `view` — побочный эффект.** Если добавить к
  `get_profile` параметр `view` с любым значением (например,
  `view=links` или вообще случайной строкой), API вместо данных всегда
  возвращает одну и ту же **схему полей** ответа, а не сами данные.
  Официального описания этого поведения нет — обнаружено опытным
  путём. Полезно, если нужно быстро посмотреть, какие поля вообще
  бывают в ответе, но не полагайтесь на это как на документированную
  фичу — сервер может это исправить в любой момент.
- **`count=true`** у `authors/search` — не возвращает список авторов,
  а только число совпадений: `[{"count": N}]`. Удобно, чтобы заранее
  прикинуть объём выдачи перед полным поиском.

## Как это использовать в `main.ipynb`

1. Раздел 1: указать `sid`, `begin_year`, `end_year` через виджеты и
   загрузить `file.csv` со списком участников школы.
2. Раздел 2: прогнать сбор данных один раз — получатся 4 JSON-файла
   (см. схему пайплайна выше). Дальше эти файлы можно переиспользовать,
   не дёргая API заново, если не менялся список авторов/`sid`/годы.
3. Раздел 3: вся аналитика (профили авторов, сравнение, кластеризация,
   динамика по годам, тренды, прогноз) работает уже только с локальными
   JSON — интернет и API больше не нужны.

## Что можно доработать (roadmap)

- Не забыть про `sid`: для каждого используемого значения должен
  формироваться свой набор JSON-файлов (сейчас имя файла уже включает
  `sid=...`, но стоит явно проверять при повторном запуске, что не
  перезатёрлись файлы от другого `sid`).
- Добавить повторные попытки (retry) при сетевых сбоях вместо простого
  `try/except` с пропуском — сейчас при ошибке автор/год просто
  теряется без предупреждения в файле.
- Кэшировать результат `get_factors` — он не меняется между запусками,
  нет смысла перезапрашивать три уровня каждый раз.
